# Кредиторы / РТК — вкладка карточки дела (apps/procedure)

Вкладка **«Кредиторы / РТК»** карточки дела о банкротстве (рабочее место юриста / помощника АУ). Была заглушкой (`PLACEHOLDER_TABS`); реализована 29.08.2026, **на проде с 31.08.2026** (коммит `a5dfbe5`, миграция `procedure/0027`). Живёт в `apps/procedure` — отдельного приложения нет: сущности привязаны к делу (`BankruptcyCase`) и переиспользуют его права, движок и стиль.

Задача вкладки — вести **реестр требований кредиторов (РТК)**: кто кредитор, куда ему писать и куда платить, сколько он заявил и какие его требования суд включил в реестр.

## Две сущности

Дерево ровно в два уровня — **кредитор (ветка) → его требования (листья)**.

### `Creditor` — кредитор

Юридическое **или** физическое лицо (`kind` = `legal` / `person`; от вида зависит только подпись поля: «Наименование юрлица» / «ФИО кредитора»).

| Поле | Смысл |
|---|---|
| `number` | **Номер кредитора** — сквозной внутри дела, присваивается автоматически (`services.next_creditor_number`, `max+1`, как исх.№ у запроса). Уникален в пределах дела (`uniq_creditor_number_per_case`) |
| `name` | Наименование юрлица / ФИО физлица |
| `legal_entity` | Связь с реестром `crm.LegalEntity` (необязательная) — из неё подтягиваются ИНН/ОГРН, адрес и банковские реквизиты |
| `inn`, `ogrn` | Реквизиты |
| `corr_address` | **Адрес для корреспонденции** |
| `bank_name`, `bik`, `settlement_account`, `correspondent_account`, `account_holder` | **Банковские реквизиты** — куда перечислять по реестру |
| `total_amount` | **Сумма требований, общая** (заявленная) |
| `contact_person`, `phone`, `email` | Контакты |
| `source` | `manual` / `questionnaire` (импорт из анкеты) |
| `notes` | Комментарий |

Свойства витрины: `included_date` (самая ранняя дата записи среди требований — она же дата включения кредитора в РТК), `claims_total` (сумма по требованиям — для сверки с заявленной), `bank_details_filled` / `bank_details_display`, `missing_fields`.

### `Claim` — требование

`1:N` к кредитору: у одного кредитора требований может быть несколько (основной долг + пени, разные договоры, разные очереди).

| Поле | Смысл |
|---|---|
| `queue` | **Очередность удовлетворения**: первая · вторая · третья — залог · третья — основной долг · третья — пени/штрафы |
| `registry_date` | **Дата внесения записи в РТК** (пусто → требование ещё не в реестре) |
| `registry_number` | **Номер кредитора по реестру** (как проставлен в самом реестре — строка, может быть «3.1») |
| `amendment_note` | **Отметка о внесении изменений** (текст) |
| `amount` | **Сумма требования** |
| `basis` | Основание (определение суда, договор, судебный приказ) |
| `notes` | Комментарий |

🛑 **Очередь — фиксированный перечень в коде** (`CLAIM_QUEUE_CHOICES`, `models.py`), а не справочник в БД: перечень нормативный (127-ФЗ, ст. 134 + залог отдельной строкой), править его в UI нельзя. Новая очередь = миграция + правка перечня.

🛑 **`registry_number` — строка, а не число**, и это НЕ `Creditor.number`. Первое — номер записи в реестре, который ведёт АУ (бывает «3.1», «2/1»); второе — наша внутренняя сквозная нумерация кредиторов дела. Оба показываются в таблице, не путать.

## Обязательные поля: где жёстко, где мягко

Регламент называет обязательными: наименование/ФИО, адрес для корреспонденции, банковские реквизиты, общую сумму требований, номер кредитора.

🛑 **На уровне модели пустота допускается — иначе не работал бы импорт из анкеты**: анкета БФЛ даёт только наименование и сумму, банковских реквизитов кредитора там нет в принципе. Требовать их в момент импорта означало бы не импортировать вовсе.

Как это разведено:
- **Жёстко (сервер)** — `name` (иначе форма возвращается с ошибкой) и уникальность `number` в деле.
- **В форме (`required` в HTML)** — наименование, номер, сумма требований, адрес, БИК и расчётный счёт: браузер не даст отправить пустыми, звёздочка `*` их помечает.
- **Витрина** — свойство `Creditor.missing_fields` собирает незаполненное, в строке таблицы это жёлтая строка «⚠ не заполнено: …». Так импортированный кредитор виден как неполный, но не блокирует работу.

У требования жёстко обязательны только **очередь** и **сумма**. Дата внесения в РТК, номер по реестру и отметка об изменениях появляются лишь после определения суда о включении — требовать их при заведении нельзя, иначе нечем было бы вести «заявлено, но ещё не включено».

## UI

Шаблоны: `templates/procedure/_tab_creditors.html` (вкладка + дерево), `_creditor_card_modal.html`, `_claim_card_modal.html`.

- **Дерево.** Одна ветка = один `<tbody class="cred-branch">`: строка кредитора + строки его требований. Каретка в первой колонке переключает класс `collapsed` на `<tbody>`, листья прячутся CSS-ом (`tbody.collapsed .claim-row{display:none}`) — без перезапросов на сервер.
- 🛑 **Подложка строки = включение в РТК**: дата внесения записи есть → **розовая**, нет → **серая**. У кредитора берётся `included_date` (самая ранняя среди требований). Цвета заданы CSS-ом в самом партиале (`#procedure-creditors .cred-row.in-rtk td{background:#fce7f3}` и т.д.), **не tailwind-классами**: нужных оттенков в собранном `static/css/tailwind.css` нет, а пересобирать его ради двух цветов незачем (и рискованно — см. гоччу пересборки в `docs/ui-conventions.md`). Листья на полтона светлее веток, чтобы дерево читалось.
- 🛑 **Колонки у листа переиспользованы под другие смыслы** (очередь / № по реестру / отметка об изменениях / основание) — поэтому у значений в строке требования стоят мелкие серые подписи (`.leaf-lbl`). Без них лист читался бы как продолжение шапки кредитора.
- **Кнопки**: «Импортировать кредиторов из анкеты» и «Добавить кредитора» — в панели над таблицей; «добавить требование» (иконка `file-plus`) и «удалить» — в строке кредитора; «удалить» — в строке требования.
- **Клик по строке → карточка** через `data-edit-url` и общий делегированный обработчик в `dashboard.html` (тот же, что у запросов и корреспонденции). Клики по кнопкам/ссылкам/полям он отсекает, поэтому каретка и иконки-действия карточку не открывают.
- **Свод** над таблицей: кредиторов / требований / в реестре / заявлено ₽ / включено в РТК ₽.

### Модалки

Обе — `<dialog class="modal modal-open">` на `body` (`hx-target="body" hx-swap="beforeend"`), сохранение `hx-target` на саму модалку с `hx-swap="outerHTML"`.

🛑 **Успешное сохранение отдаёт пустой 200 + `HX-Trigger: reloadCreditors`** — пустое тело при `outerHTML` убирает модалку, а вкладка перерисовывается сама (обёртка `#creditors-list` слушает `reloadCreditors from:body`). Тот же приём, что у `reloadRequests` в «Корреспонденции». **Не 204**: htmx на 204 не свопит вовсе, и модалка осталась бы висеть.

🛑 **Ошибка валидации возвращает модалку целиком, заполненную из `request.POST`** (контекст `v` — значения полей строками, `error` — текст). Поэтому вьюхи не отдают `HttpResponseBadRequest`: htmx на 4xx не свопит, и пользователь увидел бы «ничего не произошло», потеряв введённое.

🛑 **Суммы кладём в `value` строками с точкой** (`_creditor_values`, `str(Decimal)`): Decimal, отрендеренный под ru-локалью, получает запятую, `<input type="number">` считает такое значение невалидным и показывает поле пустым — следующее сохранение затирает сумму в NULL. Память `decimal-number-input-localization`; в шаблонах дополнительно стоит `|unlocalize`.

🛑 **Обработчики (`credToggle`, `credKindChanged`, `credClearLegalEntity`) объявлены в самих партиалах**, а не в `dashboard.html`: оболочка грузится один раз за сессию, и у всех, кто держит вкладку открытой со вчера, новой глобалки бы не было — кнопка молча ничего не делала бы (та же грабля, что с редактором запросов 28.08.2026). Слушатель тоста `procToast` вешается на `body` один раз под флагом `window.__procToastWired`, иначе перерисовка вкладки плодила бы дубли.

### Выбор кредитора из реестра юрлиц

Переиспользован пикер адресатов запросов: `openRecipientPicker(box)` / `pickRecipient(...)` из `dashboard.html` + вью `procedure:recipient_picker`. Тип запроса не передаётся → фильтра по виду ЮЛ нет, показывается весь реестр.

🛑 **Hidden-поле `legal_entity_id` лежит ВНУТРИ бокса** (`data-recip-id`) — как в карточке запроса. Снаружи `pickRecipient` записал бы выбор в форму создания запроса, которая живёт на той же странице под модалкой.

При сохранении реквизиты из выбранного юрлица подставляются **только в пустые поля** (`services.creditor_fields_from_legal_entity`) — введённое руками не затирается. Адрес берётся почтовый → юридический → фактический.

## Импорт кредиторов из анкеты

Кнопка «Импортировать кредиторов из анкеты» → `services.import_creditors_from_questionnaire`.

- **Источник тот же, что у уведомления кредиторам** — `apps.afd.isk_context.resolve_creditors` (банки, МФО, маркетплейсы, коммуналка, суды, штрафы, прочее). Единая точка: новый табличный тип долга в анкете достаточно добавить в `resolve_creditors`, и он приедет и в исковое, и в уведомления, и сюда.
- **Схлопывание по кредитору**: два кредита в одном банке = один кредитор, суммы складываются в `total_amount`.
- **Идемпотентно**: уже заведённый кредитор (по `legal_entity` либо по совпадению наименования) пропускается — кнопку можно жать после каждого уточнения анкеты. Тост говорит, сколько создано и сколько пропущено.
- 🛑 **Требования при импорте НЕ создаются.** Анкета — это заявленный долг со слов клиента, а запись РТК появляется только по определению суда о включении. Импортированный кредитор всегда серый, пока юрист не заведёт ему требование с датой.
- 🛑 **Пустая анкета — не ошибка, а частый случай.** На проде кредиторы заполнены далеко не у всех дел (при разборе «уведомления кредиторам» 29.08.2026: из 40 проверенных дел кредиторы нашлись у 3). Поэтому при нулевом результате приходит понятный тост, а не молчание.

## Вьюхи и URL

Все — `@login_required` + `@require_procedures` (право `can_access_procedures`), услуга проверяется `_bfl_service` (только БФЛ, с учётом `Service.objects.visible_to`).

| URL (`/procedure/service/<service_id>/…`) | Вьюха | Что делает |
|---|---|---|
| `tab/creditors/` | `tab_creditors` | вкладка целиком |
| `creditors/import/` | `creditors_import` | импорт из анкеты (POST) |
| `creditors/new/` · `creditors/<cred_id>/` | `creditor_form` | модалка кредитора (новый / правка) |
| `creditors/new/save/` · `creditors/<cred_id>/save/` | `creditor_save` | сохранение |
| `creditors/<cred_id>/delete/` | `creditor_delete` | удаление (требования — каскадом) |
| `creditors/<cred_id>/claims/new/` · `claims/<claim_id>/` | `claim_form` | модалка требования |
| `creditors/<cred_id>/claims/add/` · `claims/<claim_id>/save/` | `claim_save` | сохранение |
| `claims/<claim_id>/delete/` | `claim_delete` | удаление |

Сервисный слой — `apps/procedure/services.py`: `next_creditor_number`, `create_creditor`, `creditor_fields_from_legal_entity`, `import_creditors_from_questionnaire`, `add_claim`, `creditors_summary`.

Админка: `Creditor` с инлайном `Claim`, плюс отдельный `ClaimAdmin`.

## Деплой

- Миграция **`procedure/0027_creditor_claim_and_more`** — новых зависимостей нет, выкатка обычным **`deploy`** (не `rebuild`).
- Сидов и справочников не требуется: очереди — перечень в коде, кредиторы заводятся по делам.
- После выкатки — рестарт `web` (кэш шаблонов) и `Ctrl+Shift+R` у пользователей: вкладка добавлена в `card.html`, а карточка дела у открытых сессий уже загружена.
- **Выкачено на прод 31.08.2026** через agent API (`POST https://siricrm.ru/devops/agent/jobs/` с `{"action_type":"deploy","params":{"branch":"feat/production-ready"}}`, токен `DEVOPS_AGENT_TOKEN_PROD` из `.env.dev`): `git pull --ff-only` → миграция `0027` OK → рестарт `web`/`celery`/`celery-beat`/`userbot` → healthcheck 200. Раннеров арбитража и `pbx-listener` фича не касается — трогать их не надо.
- 🛑 **Поллинг статуса job'а во время рестарта `web` отдаёт пустой ответ** (не JSON) — это не ошибка деплоя, а окно, пока daphne поднимается: обработчик опроса должен переживать пустое тело и продолжать опрашивать.
- 🛑 `PLACEHOLDER_TABS` в `apps/procedure/views.py` теперь **пустой словарь**: «Кредиторы / РТК» была последней заглушкой, ссылка на вкладку прописана в `card.html` явно. Вью и URL `tab_placeholder` оставлены под будущие вкладки.

## Что не сделано (следующие шаги)

- **Реестр требований как документ** — печатная форма РТК (Приказ Минэкономразвития № 234) из этих данных; сейчас вкладка только ведёт учёт.
- **Связь с запросами**: у кредитора нет кнопки «написать уведомление» — уведомления кредиторам по-прежнему создаются из «Корреспонденции» и берут кредиторов из анкеты, а не из этой вкладки. Логичный следующий шаг — переключить `services.case_creditors` на `Creditor` дела с фолбэком на анкету.
- **Сверка сумм**: `claims_total` показывается рядом с заявленной суммой, но расхождение никак не помечается.
- **Импорт из ответов госорганов / определений суда** — вручную.
- **Событийка и уведомления**: включение требования в реестр не пишется в `ClientLogEntry` и не шлёт уведомление.
- **Проверка на потоке**: вживую в браузере вкладка ещё не обкатана. Проверено на dev автотестом (создание/правка/удаление кредитора и требования, отказ по дублю номера, отказ по неверной очереди, импорт из анкеты 5 кредиторов и его идемпотентность, каскадное удаление требований), на проде после деплоя — рендер вкладки, модалки нового кредитора и наличие вкладки в шапке карточки дела. На проде на 31.08.2026 в таблицах `procedure_creditor`/`procedure_claim` пусто — данные заводят юристы.
