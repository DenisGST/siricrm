# Коммерсантъ — публикации в газете (`apps/kommersant`)

Модуль публикаций сведений о банкротстве в газете «Коммерсантъ» (bankruptcy.kommersant.ru).
Под-вкладка **«КоммерсантЪ»** вкладки «Публикации» карточки дела БФЛ (раньше была заглушка
внутри `apps/efrsb`, теперь отдельное приложение). Брат `apps/efrsb`, но с денежным контуром.

Разработано по трём задачам: (1) генерация текста публикации для введения реализации/
реструктуризации, (2) отправка запроса счёта по email, (3) приём счёта по email.
Разведка по возможности интеграции — см. память `kommersant-integration-research`.

## Полный жизненный цикл публикации

**текст → бланк заявки → отправка в ИД → счёт → оплата → выход в номере**

Статусы `KommersantPublication.status`: `draft → generated → sent → invoiced → paid → published`
(+ `cancelled`). 🛑 Статусы денежного контура (`sent`/`invoiced`/`paid`) **раздельные**, а не
схлопнуты в «отправлено» — по ним юрист видит, где застряла публикация.

🛑 **Главное отличие от ЕФРСБ — ДЕНЕЖНЫЙ КОНТУР.** Публикация платная и предоплатная
(~8–12 тыс ₽; тариф 367,33 ₽/кв.см с 08.05.2026, индексируется ежегодно): деньги должны
поступить на счёт АО «Коммерсантъ» **не позднее 14:00 мск** даты окончания приёма сообщений,
иначе публикация уедет в следующий номер. Газета с объявлениями выходит **по субботам**.

## Как вообще можно интегрироваться (итог разведки)

У ИД «Коммерсантъ» три канала (память `kommersant-integration-research`):
1. **Подача заявок** — сервис **«Ъ-Публикатор»** (машинный API существует — его интегрировал
   конкурент ПАУ), спека не публична, запрос в ИД отправлен 20.07.2026. **Пока работаем по
   официальному email-регламенту** (`bankruptcy.kommersant.ru/index.php?publemail`).
2. **Чтение** — платная XML/CSV-выгрузка всего реестра (100 000 ₽/мес), нам не нужна:
   Ъ-Публикатор и так вернёт статус наших публикаций, а сайт парсить нельзя
   (`robots.txt` = `Disallow: /` + просмотр по платной подписке).
3. **Закрывающие документы** — бесплатно через ЭДО Диадок (АО «Коммерсантъ», ИНН 7707120552).

## Модели (`models.py`)

- **`KommersantMessageType`** — DB-editable каталог типов сообщений (DRAFT, правится в
  Справочниках/админке). `text_template` — шаблон текста с плейсхолдерами; `blank_checkbox`
  (`restructuring`/`realization`) — какой из двух взаимоисключающих чекбоксов бланка ФЛ отмечать;
  `applicable_kinds` — фильтр по виду процедуры.
- **`KommersantPublication`** — заявка и её жизненный цикл. Блоки полей: наш контент
  (`text`/`overrides`/`accounting_docs_to`), бланк (`blank_docx`/`blank_pdf` → StoredFile),
  отправка (`sent_at`/`sent_message_id`/`send_error`), счёт (`invoice_*`/`invoice_file`/
  `invoice_message_id`), оплата (`is_paid`/`paid_date`), публикация (`publication_date`/
  `newspaper_number`/`announcement_number`).
- **`KommersantAttachment`** — подтверждающие документы, уходящие письмом (судебный акт о
  введении процедуры, акт о полномочиях АУ). 🛑 ИД отказывает в публикации при их отсутствии,
  поэтому состав вложений — часть заявки, а не «файлы где-то в деле».

## Задача 1 — текст сообщения (`generator.py`)

- 🛑 Базовый контекст **переиспользуется из `apps.efrsb.generator.build_context`** — набор
  плейсхолдеров (должник/ФУ/СРО/суд/дело) там ровно тот же; дублировать 30 ключей и потом
  расходиться в формулировках хуже, чем импорт между модулями. Сверху добавлены поля бланка:
  `контакты АУ`, `контакты должника`, `прежнее ФИО`, `адрес фактический`, `утверждён ФУ`.
- `check_problems(case, mt, keys=…)` — показывает ТОЛЬКО незаполненное/невалидное, строго по
  плейсхолдерам конкретного шаблона (или по переданному `keys` для предпроверки бланка).
- 🛑 **Требования ИД к тексту** (п. 4 Порядка, Приказ Минэкономразвития РФ от 12.07.2010 № 292):
  сокращения запрещены, кроме предусмотренных НПА → в шаблонах раскрыты («года рождения»,
  «электронная почта»). ИД вправе отказать, если по сообщению нельзя опознать должника и
  управляющего (п. 8 ст. 28 ФЗ № 127-ФЗ) → `check_problems` строгий на ИНН/СНИЛС/адрес.
- 🛑 **Языковые грабли** (проверено на реальном деле): после «Решением/Определением» берём ключ
  `{арбитражного суда}` (родительный), иначе «Решением Арбитражный суд»; ФИО подставляется в
  именительном и **не склоняется** → фраза построена через тире; `{утверждён ФУ}` = «утверждён/
  утверждена» по отчеству АУ (эвристика в `_fu_approved`, при промахе правится в тексте).
- Шаблоны — DRAFT, засеяны `kommersant_seed` (реализация + реструктуризация), правятся в справочнике.

## Задача 2 — бланк заявки + отправка (`blank.py`, `mailer.py`)

### Бланк заявки

- Официальный бланк ИД для ФЛ (`bankruptcy.kommersant.ru/files/sbk.blanks/blank-person.docx`) →
  шаблон **`OLD/Коммерсант/Заявка Коммерсантъ (ФЛ) — шаблон.docx`** (в репо).
- 🛑 **В оригинале поля — Word content controls (`<w:sdt>`), которые `render_docx` НЕ видит**
  (python-docx не отдаёт run'ы внутри sdt). В шаблоне они развёрнуты в обычные run'ы, а
  тексты-заглушки заменены на плейсхолдеры `{…}`. Конвертер оригинала —
  `scratchpad/make_blank_template.py` (разворачивает sdt + подставляет 24 плейсхолдера по
  порядку следования). **ИД поменяет бланк → перегенерировать шаблон, не править код.**
- Чекбоксы бланка (`☒`/`☐`): вид процедуры (по `blank_checkbox` типа) + «отчётные документы на
  АУ/должника» (по `accounting_docs_to`).
- Факсимиле АУ (`ArbitrationManager.signature_file`, PNG) вставляется в строку подписи (последняя
  таблица бланка); файла нет/недоступен → документ отдаётся без подписи, формирование не падает.
- Итог: `.docx` (с факсимиле) + `.pdf` (LibreOffice `docx_to_pdf`), оба подшиваются в папку
  клиента **«Публикации Коммерсантъ»** + событийка `kommersant_blank_created`.

### Отправка письма

- 🛑 **Почта — с ЛИЧНОГО ящика сотрудника-АУ, не системного** (заявку подаёт управляющий, счёт
  ИД шлёт ответом ему же). Своей почты у проекта нет вообще — глобальный `EMAIL_BACKEND` не
  подходит. Транспорт `mailer.py` работает с `mail_accounts.MailAccount` (dataclass с уже
  расшифрованным паролем и хостами), а не с моделью.
- В письме (регламент ИД): подписанный PDF заявки + та же заявка `.docx` + подтверждающие
  документы. Message-ID сохраняется в `sent_message_id` — по нему ловим ответ со счётом.
- 🛑 **SMTP/IMAP только в Celery** (`tasks.py:send_request` / `poll_invoices` / `fetch_invoice_now`)
  — в ASGI такие операции вешали daphne (инцидент WA-вебхука 09.06.2026). Ошибка транспорта →
  `send_error` (иначе вечное «отправляется» в UI). SETNX-лок от двойной отправки.

## Почтовые креды АУ — в ПРОФИЛЕ сотрудника

- 🛑 Креды вводит сам АУ в **личном профиле** (`/profile/` → карточка «Почта для публикаций в
  «Коммерсантъ», видна только при `Employee.is_arbitration_manager`, `role="arbitration"`):
  `Employee.kommersant_email` + `kommersant_password_enc` (Fernet, `apps.core.crypto` — зеркало
  кредов ЕФРСБ). View `core:profile_kommersant`, партиал `_profile_kommersant.html`. Пароль
  write-only (пусто = не менять, галочка = стереть).
- 🛑 **Пользователь вводит ТОЛЬКО email и пароль.** SMTP/IMAP-хосты выводятся из домена адреса
  (`mail_accounts.hosts_for_email`): таблица Яндекс / Mail.ru-группа (mail.ru/bk.ru/inbox.ru/
  list.ru/internet.ru) / Rambler / Gmail + фолбэк `smtp.<домен>`/`imap.<домен>`; порты 465/993 SSL.
- 🛑 **Связь дела с ящиком**: `Procedure.arbitr_manager` → `ArbitrationManager.employee` → его
  почта из профиля. Внешний АУ без привязанного сотрудника заявку через CRM подать не может
  (UI подскажет). `mail_accounts.account_for_manager(am)` / `account_for_employee(emp)` →
  `MailAccount | None`.
- 🛑 Яндекс/Mail.ru требуют **пароль приложения**, не пароль аккаунта, и включённый IMAP.

## Задача 3 — приём счёта (`mailer.fetch_replies` + `services.ingest_invoice`)

- Beat **`kommersant-poll-invoices`** каждые 15 мин (миграция `kommersant/0002`) → `poll_invoices`:
  собирает сотрудников-АУ, у кого есть ожидающие заявки (`status=sent`, `invoice_received_at` пуст),
  и опрашивает их ящики. Вхолостую в почту не ходит (нет заявок → сразу выходит).
- 🛑 **Матчинг строго по In-Reply-To/References** (`fetch_replies`), НЕ по теме: тема у ИД любая,
  а привязать чужой счёт к делу хуже, чем не привязать никакого.
- Номер/дату/сумму счёта тянем эвристикой из тела письма (`parse_invoice_meta`); не нашли →
  оставляем пустым, юрист впишет (по номеру счёта идёт назначение платежа, выдумывать нельзя).
- `ingest_invoice` идемпотентен по Message-ID ответа (повторный проход не плодит дублей); счёт
  подшивается в S3 + папку «Публикации Коммерсантъ» + событийка `kommersant_invoice_received`.
- `looks_like_invoice` отсекает автоответы «письмо получено» (нужно вложение-документ + признаки
  счёта в имени/теме/теле).

## UI (под-вкладка + 5 модалок)

- `_subtab_kommersant.html` — реестр публикаций (статус, заявка, счёт, публикация, действия) +
  строка готовности почты АУ. Самоперезагрузка по `reloadKommersant`, тост `kommersantToast`
  (обработчик в `dashboard.html`).
- Модалки: текст сообщения (`_publication_form_modal` + генерация), «текст целиком»
  (`_publication_text_modal`, копирование), предпроверка отправки (`_send_modal` — блокеры +
  состав письма + приложить вложения), счёт/оплата (`_invoice_modal`), выход публикации
  (`_published_modal`). Все — `<dialog class="modal modal-open">`, скрипты в IIFE.
- 🛑 Отметка публикации пишет `Procedure.publication_kommersant_date` + `recompute_due_dates` —
  это якорь мероприятий-сроков процедуры.

## Сид, зависимости, деплой

- **`python manage.py kommersant_seed`** — типы сообщений (реализация/реструктуризация, DRAFT) +
  типы лога. Идемпотентно; `--force-templates` перезаливает формулировки. 🛑 В deploy-handler
  НЕ входит (как `procedure_seed`/`efrsb_seed`) — гонять руками при выкатке.
- **Зависимостей нет** (`imaplib`/`smtplib` — stdlib) → обычный **`deploy`**, не rebuild.
  🛑 Но образ должен иметь `bleach`/`Markdown` (модуль вики) — если сервер не пересобирали после
  вики-коммита, `deploy` упадёт на импорте: нужен **`rebuild`**. Проверка: `pip show bleach`.
- Миграции: `core/0036` (поля Employee) + `kommersant/0001,0002`. После деплоя: `kommersant_seed`
  + рестарт `celery`/`celery-beat`. Заполнить почту АУ в профиле на КАЖДОМ сервере (per-DB).
- Шаблон бланка (`OLD/Коммерсант/*.docx`) — в репозитории, `blank.py` читает его с диска.

## Что НЕ сделано / проверено частично

- **Отправка/приём письма вживую не тестировались** — почтовых кредов АУ пока нет ни у одного
  сотрудника. Код, задачи Celery, UI, предпроверки работают; реального обмена с `pb@kommersant.ru`
  не было. Первую заявку отправлять под присмотром.
- **Факсимиле на dev не проверить** — подпись АУ лежит в прод-бакете S3 (dev-ключи → AccessDenied);
  деградация «без подписи» отработала, на проде подтянется.
- Формулировки шаблонов — **DRAFT**, подтвердить с АУ.
- Бланк только для **ФЛ** (blank-person). Для ЮЛ (blank-company) — при необходимости отдельный шаблон.
- **«Ъ-Публикатор»** (машинная подача) — когда ИД пришлёт спеку, заменить email-подачу на API.
